Architecture

A modular monolith, deliberately

One deployable Laravel app, split internally into eight bounded modules that talk to each other only through Actions and domain events. Microservices were rejected: coordinating “charge the buyer, pay the seller, advance the commission” across a network is a correctness nightmare for zero benefit at this scale.

Module dependency rule

Modules may call another module's Actions or subscribe to its events — never reach into another module's models directly. Example real edges:

Identity FollowUser → emits UserFollowed Social listens → notifies followed user Catalog PieceApproved → Discovery flushes cache Social LikePiece → counter listener (+1 atomic) Moderation ResolveReport → Catalog takedown

Cross-cutting seams (interfaces) keep vendors swappable:

PaymentGateway → FakeGateway | StripeGateway PieceSearcher → MysqlFulltextSearcher | Meilisearch later Clock → SystemClock

Swapping any of these is a container binding change — no domain edits.

Guarded lifecycles

Three state machines make illegal flows impossible

Built on spatie/laravel-model-states. A transition that isn't registered simply doesn't exist — you cannot ship before the balance clears or approve before a proof arrives. Press ▶ on any machine to watch a legal play-through animate; click any node to see what it allows.

Key flows, step by step

Each card opens to the exact call chain — who calls what, in order, with the guard rails called out. Click a header to expand.

1

🛒 Ready-made purchase — two sellers, one payment, correct split

›
Browser
POST /cart/{piece} → CartController@add → AddToCart — rejects own/sold/unapproved/commission-only pieces, insertOrIgnore into cart_items.
Buyer
GET /checkout → CartQuery::for() groups cart by seller, adds flat shipping per group, computes totals.
Buyer
POST /checkout → CheckoutController@store validates address (saved or new), StartCheckout::handle(): verifies every seller stripe_charges_enabled, creates Order + OrderSeller groups + OrderItem snapshots inside a transaction, generates checkout_ref.
Gateway
PaymentGateway::createCheckoutSession($order) → redirect away (Stripe hosted / fake-pay route locally).
Settlement
POST /webhooks/stripe (or fake-pay) → MarkOrderPaid::handle(gateway, eventId, …): insertOrIgnore into processed_webhooks — a replay returns the same order untouched; row lock guards double-settlement.
Effects
Inside the same transaction: state → paid, sold_at stamped on every item's piece, cart cleared, then FulfillTransfers fans out per seller group (distinct transfer refs).
Notify
OrderPaid notification → buyer ×1, each seller ×1 (database + mail).
Fulfil
Each seller sees only their group at /studio-orders → ShipSellerGroup records shipped_at + tracking.
Refund
Admin-only RefundOrder: reverses transfers first, state → refunded, sold_at = null re-lists every piece, parties notified.
2

🎨 Custom commission — request → quote → proof loop → completion

›
Buyer
POST /commissions/request/{seller} → RequestCommission: rejects self-request, creates CM-#### in requested, seller notified.
Seller
QuoteCommission (policy manageAsSeller): quote_minor stored, deposit_minor = round(30%), state → quoted, buyer notified. Or DeclineCommission with reason → thread message.
Buyer
PayCommissionCapture(deposit): processed_webhooks claim → state must be quoted else rollback of the claim row → deposit_paid, seller notified. Replay = same commission back, zero effects.
Seller
StartCommissionWork → in_progress. Then SubmitCommissionProof(image, note): private-disk write commissions/{id}/{uuid}.jpg, versioned CommissionProof, state → proof_submitted, buyer notified.
Buyer
RequestCommissionRevision(note) → revision_requested + thread message (one correction hop), or ApproveCommissionProof → approved, seller told “balance pending”.
Money
PayCommissionCapture(balance): refuses unless approved — then createCommissionTransfer moves the payout. This is the only point money reaches the seller.
Close
ShipCommission(tracking) → shipped; CompleteCommission(buyer confirms) → completed. Buyer can now post the verified Review (below).
Chat
Any party: PostCommissionMessage → CommissionMessage row + counterparty notified. Proofs stream through CommissionProofController@show — Gate:view + private disk, never public URLs.
3

🖼️ Publish → moderate → appear in feed (or get taken down)

›
Seller
/create or studio panel → CreatePiece: transaction wraps the row + MediaPipeline.attach() — originals private, GD watermarked 480/960 derivatives public. Lands in draft.
Seller
PublishPiece → pending_review (Draft/PendingReview transition only).
Admin
Filament queue /admin/pieces: ApprovePiece (sets reviewed_by/at, published_at, dispatches PieceApproved) or RejectPiece(reason).
Events
FlushDiscoveryCache forgets the cached first-page ID list — next anonymous home request rebuilds it fresh.
Takedown
Report resolved on an approved piece → ResolveReport flips approved → rejected with reason; discovery cache flushed again.
4

❤️ Social interactions — likes, saves, follows, comments

›
Livewire
LikeButton::toggle() → LikePiece uses firstOrCreate + wasRecentlyCreated — a double click can never double count. Emits PieceLiked.
Listener
UpdatePieceCounters maps event → column and runs a single UPDATE … SET likes_count = likes_count ± 1 — atomic under concurrency.
Save
SaveToBoard: syncWithoutDetaching onto the board; a piece counts saved once per user across boards — UnsaveFromBoard decrements only after the last holding board lets go.
Comments
AddComment enforces one reply level (parent.parent_id ≠ null rejected), notifies artist and/or parent author, skips self-notifications.
Follow
FollowUser emits UserFollowed; Identity's own listener sends NewFollower to the followed user.
5

⭐ Verified review + abuse triage

›
Gate
CreateReview requires actor == commission.buyer AND state == completed; rating 1..5; firstOrCreate keyed on unique commission_id — second review throws already_reviewed.
Display
Profile aggregates AVG/COUNT from reviews; every entry carries the verified-buyer badge because existence implies a completed, paid commission.
Report
SubmitReport morphs onto Piece/User with whitelisted reasons, RateLimiter 5/hour/user; lands pending in /admin/reports.

Code review guide

How to read this codebase like its author

A repeatable pass for reviewing any feature — plus the conventions every file follows.

The six-step review pass

  1. Find the Action. Start from the route in routes/web.php, jump to the controller, and confirm it delegates to exactly one Action in app/Domain/<Module>/Actions. If business logic lives in the controller, that's a finding.
  2. Check authorization at the data layer. The Action should call Gate::forUser($actor)->authorize(...) or the controller should use a Form Request's actor(). UI hiding is not security — verify the policy exists in AppServiceProvider::boot.
  3. Verify the state boundary. If the flow touches a machine (Piece/Order/Commission), confirm every transition used is registered in the base state class config() and illegal paths throw TransitionNotFound.
  4. Follow the events. What fires after success? Check listeners exist and are wired in AppServiceProvider (counters, cache flushes, notifications). Money-critical writes must claim their idempotency row first (processed_webhooks).
  5. Check the tests tell the story. Each phase has a Feature test named after the DoD. The test should read as the specification — if you can't understand the feature from the test alone, the test is the finding.
  6. Run the gates. All four must pass before merge (commands below). Larastan runs at max level — new mixed-typed shortcuts will fail it by design.

Conventions you'll see everywhere

Naming
Actions = verb phrases Requests = *Request + actor()/data() States = past/participle nouns lang files mirror modules
Boundaries
Controllers: parse → delegate → redirect No raw request arrays in Actions Never cross modules via models directly
